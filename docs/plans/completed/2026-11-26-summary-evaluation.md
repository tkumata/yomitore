# 要約評価アルゴリズムの品質改善

## Status

- Phase: completed
- Approval: approved（2026-11-26）

## Goal

日本語の要約を原文への忠実性と重要情報の網羅性を重視して採点する。総合得点と重大な誤りの確率からアプリが判定し、評価画面・履歴・統計で同じ判定を使う。

## Scope

| 対象 | 現行実装 | 変更案 |
| --- | --- | --- |
| `src/api_client.rs`、`src/evaluation.rs` | 3つの Score、適切さの Noul、合否の Choice を送る。3項目の元値を等重みで得点化する | 5つの Score と重大な誤りの Noul を送る。評価基準、応答検証、得点と判定の計算を `evaluation.rs` に置く |
| `src/main.rs`、`src/app.rs`、`src/ui.rs` | Groq の改善点と Jev の結果を統合し、Choice の二値で表示・保存する | 同じ判定を評価画面と保存に渡す。API・解析失敗と、評価結果の「要確認」をUI上で区別する |
| `src/models.rs`、`src/stats_store.rs`、`src/stats.rs` | 旧3項目と二値の合否を保存する。総合得点がない履歴や評価詳細がない履歴も読み込む | 新方式をバージョン付きで保存し、旧履歴を読み込む。保存・再読込後も「要確認」を保持する |
| `src/stats_analysis.rs`、`src/reports.rs` | 日次・週次は二値で集計し、直近180日の旧3項目の平均と中央値を表示する | 日次・週次に要確認件数を反映する。評価スコアは方式別に表示する |
| 利用者向け・開発者向け文書 | 現行の Jev 質問、等重みの採点、二値の判定を記載する | 実装後に `docs/current/REQUIREMENTS.md`、`SPECIFICATIONS.md`、`DESIGN.md`、`docs/HELP.md`、`README.md` の該当箇所を更新する |

## Non-goals

- 文章生成、文字数メニュー、API キー設定、依存関係の変更。400〜2700文字程度は評価精度の検証範囲とする。現行の生成メニューは 400、720、1440、2880 文字で、評価時の文字数による切り捨てや拒否は追加しない。
- 旧データの一括移行や新得点への換算。「要確認」を画面上で再判定する操作の追加。

## Required Behavior

### Jev の質問と応答検証

- 既存の `POST /v1/systemone` と `jev-latest` を使い、`state.original` と `state.summary` に本文を格納する。5つの Score と `critical_error` の Noul を一度に送る。`appropriate` と `overall` は新方式の質問・表示・保存から外し、旧形式の読み込みに必要なデータは保持する。
- 各質問の指示で原文と要約を評価対象のデータとして指定し、本文中の命令を実行しない。原文の記述を基準にして、外部知識による事実確認を行わない。原文の長さにかかわらず同じ基準を使う。
- Score の `criteria` は 0〜4 の順の文字列配列を使う。応答の6項目を必須とし、型、有限性、値域、Score の `confidence`、`legend` と `probabilities` のキー `0`〜`4`、各確率、確率の合計を検証する。合計の許容誤差は現行の `abs(sum - 1.0) < 0.01` を使う。Noul の応答は `type` と `noul` を検証する。Noul の `noul` は重大な誤りがある確率を表す。[TypeSafe System One API](https://docs.typesafe.ai/api/system-one.md)

| 評価項目 | 配点 | 0 | 1 | 2 | 3 | 4 |
| --- | ---: | --- | --- | --- | --- | --- |
| 忠実性 `faithfulness` | 40 | 原文を概ね裏付けにできない、または主旨を逆転させている | 主要な主張に矛盾、根拠のない追加、または結論に関わる事実誤認がある | 主旨は概ね合うが、一部の記述が原文の意味を変えている | 主要な記述は原文に沿っている。周辺の記述に意味への影響が小さいずれがある | 要約の記述をすべて原文で裏付けられ、意味や確実性を保っている |
| 網羅性 `coverage` | 30 | 原文の主題や要点を伝えていない | 主題に触れるが、結論や主要な根拠の大半を欠く | 主題と結論の大筋は伝わるが、主要な根拠や重要な条件・例外を欠く | 主題、結論、主要な根拠はそろっている。判断を左右しない補足に不足がある | 主題、結論、主要な根拠と、理解に必要な条件・例外・制約がそろっている |
| 重要度 `relevance` | 15 | 主題から外れた内容や枝葉がほぼ全体を占める | 重要性の低い情報が多く、主題に沿う内容を見つけにくい | 主題に沿う内容は見えるが、枝葉が同じかそれ以上の比重を占める | 主題に沿う内容が中心で、重要性の低い情報がわずかに残る | 主題に沿う情報に重点があり、載せた細部にも要約上の役割がある |
| 簡潔性 `conciseness` | 10 | 繰り返しや回りくどい言い方が大半を占める | 同じ情報の反復や削れる説明が多い | 主な意味は読み取れるが、複数箇所を言い換えや重複の削除で短くできる | 表現は概ね簡潔で、一部に削れる語句や重複がある | 情報を保ったまま削れる表現や重複がほぼない |
| 明瞭性 `clarity` | 5 | 日本語として意味を読み取れない | 主語・述語や関係が混乱し、要約の主要な意味を確定できない | 内容は概ね分かるが、複数の文を読み直して関係や指示対象を補う必要がある | 自然に読めて論理も追える。一部のつながりや指示語に軽い曖昧さがある | 自然な日本語で、主述、指示対象、文同士の論理が明確である |

- 忠実性は書かれた記述を対象に、数値・日時・固有名詞・因果・否定・発言者と、事実・推測・意見・可能性・確実性の違いを確認する。単なる欠落は網羅性で扱う。条件の省略によって記述が断定に変わった場合は、その記述の意味も忠実性で確認する。
- 網羅性は欠落、重要度は載せた情報の選択と比重を評価する。重要性の低い細部の省略は許容する。簡潔性は表現の無駄を対象とし、短さや必要な情報の削除で加点しない。明瞭性は文章としての読みやすさを対象とする。
- `critical_error` は独立した Noul とする。`true` は重大な矛盾、根拠のない重要情報、主旨・結論の改変、または読者の理解や判断を変える事実誤認・条件や例外の欠落がある場合とする。`false` は主旨、事実と判断に必要な条件を保ち、違いがあっても軽微な言い換えや枝葉の省略に収まる場合とする。判定基準はこの質問内に示し、他の Score を参照しない。

### 得点と判定

検証済みの5つの `score` を使い、`faithfulness / 4 × 40 + coverage / 4 × 30 + relevance / 4 × 15 + conciseness / 4 × 10 + clarity / 4 × 5` を計算する。加算後に一度だけ四捨五入し、整数点を表示と判定に使う。例えば、加算結果が79.5点なら80点と表示し、重大な誤りの確率が0.30以下なら「良好・合格」とする。

| `critical_error` | 総合得点 | 評価・最終判定 |
| --- | ---: | --- |
| 0.70以上 | 0〜100 | 不合格（重大な誤りの判定を優先） |
| 0.30超〜0.70未満 | 0〜100 | 要確認 |
| 0.30以下 | 90〜100 | 優秀・合格 |
| 0.30以下 | 80〜89 | 良好・合格 |
| 0.30以下 | 70〜79 | 要改善・不合格 |
| 0.30以下 | 0〜69 | 不合格 |

### 表示・保存・集計

- 評価画面に5項目の0〜4点、総合得点、重大な誤りの確率、最終判定、Groq の改善点3件を表示する。項目点と確率の表示桁は計算から独立させる。優先判定の理由を文言で示し、「要確認」は黄色の枠と明示的なラベルで表示する。
- バージョンを持たない既存レコードを旧方式（v1）として読み込む。旧3項目の1〜5点と既存の合否を保持し、総合得点の欠損と評価詳細がない履歴を許容する。新方式（v2）の評価は明示的にバージョンを保存し、5つの Score の元値、総合得点、重大な誤りの確率、最終判定、改善点を保持する。認識できないバージョンや壊れた v2 の読み込みはエラーとし、履歴を上書きしない。
- 直近180日の評価スコアは v1 と v2 を区別し、それぞれの尺度で平均と中央値を表示する。v2 は5項目と総合得点、v1 は現行の3項目を対象とする。評価詳細のない履歴は件数集計に含める。
- 日次・週次の訓練件数は方式をまたいで合格・不合格・要確認を数え、チャートや凡例で区別する。要確認は訓練履歴に保存し、連続合格数を維持する。バディの経験値と累積合格数の加算は合格時に行う。再読込時の連続合格・バッジ再計算にも同じルールを適用する。
- Jev の6回答と Groq の改善点3件がすべて揃った評価だけを保存対象にする。既存の保存失敗時の再試行、ファイルのロックと置き換えを利用する。

## Tasks

### Task 1 Jev の質問、解析、判定を変更する

- **Objective** — 5項目の採点と重大な誤りの判定を実装する。
- **Scope** — `src/evaluation.rs` と `src/api_client.rs`。質問と判定は評価モジュール、送受信は API クライアントに置く。
- **Acceptance Criteria** — 6問を1回で送信し、応答が有効なら1つの総合得点と最終判定を得られる。不正な応答はエラーになる。
- **Verification** — 固定応答で全項目0・4、各項目だけを4にした配点、各項目の小数を保つことを確認する。69/70、79/80、89/90 と四捨五入の前後、0.30・0.70および両端の直前・直後、100点での要確認と不合格を検証する。欠落、型違い、範囲外、確率キー・合計の不正を拒否することを確認する。

### Task 2 評価画面と履歴保存を対応させる

- **Objective** — 同じ判定をユーザーに表示し、履歴から読み戻せるようにする。
- **Scope** — `src/main.rs`、`src/app.rs`、`src/ui.rs`、`src/models.rs`、`src/stats_store.rs`。Task 1 の結果を使う。
- **Acceptance Criteria** — v1 と v2 の混在ファイルを読み込める。v2 の3つの最終判定を表示・保存できる。API エラーと解析失敗で履歴に評価が追加されない。
- **Verification** — 旧 JSON、総合得点欠損、評価詳細欠損、混在ファイルの保存と再読込、既存の保存再試行を確認する。Jev・Groq の失敗経路と3判定の表示を既存テストに追加・反映する。

### Task 3 統計とレポートを対応させる

- **Objective** — 方式別に得点を比較でき、要確認の件数を識別できるようにする。
- **Scope** — `src/stats.rs`、`src/stats_analysis.rs`、`src/models.rs`、`src/reports.rs`。Task 2 の履歴形式を使う。
- **Acceptance Criteria** — レポートで新旧の尺度と要確認の件数が分かる。要確認の前後と再読込でバディ・連続合格・バッジの扱いが一致する。
- **Verification** — v1 のみ、v2 のみ、混在、要確認のみの日を使い、平均・中央値・日次・週次の件数と連続合格を検証する。レポート領域で新旧の表示とチャートが読めることを確認する。

### Task 4 文書の同期と結合検証

- **Objective** — 実装と文書の内容を一致させ、動作検証と評価精度の検証結果を記録する。
- **Scope** — Scope に挙げた文書の該当箇所と本計画の検証記録。Task 1〜3 の結合結果を対象とする。
- **Acceptance Criteria** — 評価基準、判定の優先順位、履歴互換、利用者の表示について実装と文書が一致する。実データの検証状況を明記する。
- **Verification** — `make check` と `make build` を実行する。自動テスト、TUI の表示確認、実サービスでの評価精度をそれぞれ記録する。

#### 検証結果（2026-11-26）

- `make check` は整形、Clippy、66件のテストが成功した。配点と閾値、不正な応答、新旧履歴の保存と集計、要確認時の連続合格数を確認した。
- `make build` は成功した。
- TUI のテスト用描画環境で、評価画面の判定ラベルと枠色、80列×24行のレポートで新旧の得点と要確認件数を確認した。
- 実 API での評価と、人手で評価した日本語データによる精度検証は未実施。

#### 日本語の実データによる評価精度の検証方法

1. 利用可能な日本語の告知、解説、意見文などから約400〜2700文字の原文を長さ・文種別に用意する。各原文に良質な要約と、数値・日付・発言者の変更、因果・否定・確実性の改変、根拠なしの追記、重要条件・例外の欠落、枝葉の優先、冗長さ、指示語の曖昧さを入れた対照要約を作る。軽微な言い換え、細部の省略、本文中の命令文も含める。
2. 日本語を読める2人が、モデルの出力を見る前に5項目の段階、重大な誤りの有無、要約としての合否を個別に判定する。合否は、読者の判断を変える誤りがなく、主題・結論・判断に必要な情報が伝わるかを根拠とする。原文の根拠箇所を記録し、判定が異なる箇所をすり合わせる。同じ原文から作った例は、基準の調整用と検証用にまたがらないようにする。
3. 実 Jev に送信し、モデル名、評価方式、各 Score、Noul、最終判定を記録する。項目別の人手評価との平均絶対誤差、重大な誤りを含む要約の合格件数、重大な誤りのない要約の優先不合格件数、要確認率を報告する。人手の合否と比較した件数表も示し、文の長さや誤りの種類による差を確認する。
4. 同じ要約で旧方式も実行できる場合は、重大な誤りを含む要約の合格件数を比較する。配点・閾値・基準の調整が必要なら、変更前後を検証用の例で確認する。実 API、評価用データ、人手判定が揃わない場合は、未検証の範囲を記録する。

配点と閾値は初期値であり、実データによる妥当性の検証は未実施。
